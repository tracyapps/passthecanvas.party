# Floating toolbox windows

Research checked November 6, 2026. The desired desktop experience is several independent, draggable and resizable toolboxes across monitors, with transparent space around the cutout artwork and an optional always-on-top setting.

## Available approaches

| Approach | What it provides | Limits for this toolbox |
| --- | --- | --- |
| Browser popup | Several windows that users can move and resize, including onto another monitor. A user action can request a compact popup. | Browser chrome, dimensions and popup treatment remain browser-controlled. The page has no standard desktop transparency or general always-on-top API. Opening needs user activation and may be blocked. Keep an in-party panel fallback. [Window.open](https://developer.mozilla.org/en-US/docs/Web/API/Window/open) |
| Installed PWA | An app window without the ordinary tab and URL bars. Window Controls Overlay can extend the design into the title bar while preserving system controls. | Installation and overlay support vary. This remains a rectangular web app window. The display and overlay APIs do not expose arbitrary desktop transparency, shape, or general always-on-top controls. They improve presentation but cannot supply the entire desired window behavior. [Manifest display](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display) · [Window Controls Overlay](https://developer.mozilla.org/en-US/docs/Web/API/Window_Controls_Overlay_API) |
| Document Picture-in-Picture | An interactive HTML toolbox in an always-on-top window that the user can resize and move. | At most one per originating tab. Browsers may impose a global limit too. The website cannot set screen position, the window closes with its opener, and support remains limited. Browser framing and a rectangular surface remain. Use it for one consolidated toolbox if supported. [Specification](https://wicg.github.io/document-picture-in-picture/) · [Compatibility and behavior](https://developer.mozilla.org/en-US/docs/Web/API/Document_Picture-in-Picture_API) |
| Electron desktop app | Multiple frameless transparent windows, native positioning and always-on-top controls. Can reuse the Svelte UI in a bundled Chromium runtime. | Electron documents transparent-window resizing limitations. Transparent pixels do not automatically pass clicks through. Experimental native window shaping is Windows/Linux only, so a Mac cutout needs visual transparency with separately designed input handling. A target-OS prototype must establish resizing behavior before a promise of full parity. [Window styles](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles) · [Native shape and stacking](https://www.electronjs.org/docs/latest/api/base-window) |
| Tauri desktop app | Multiple native webview windows with transparency, decorations, drag, resizing, position and always-on-top controls. Uses the system webview. | Runtime differences across macOS, Windows and Linux need verification. The documented window API exposes whole-window cursor ignoring rather than an alpha-mask shape API. Transparent appearance, resizing and input passthrough need testing together. [Window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/) · [Webviews](https://v2.tauri.app/reference/webview-versions/) |

A permission-gated Window Management API can help supported desktop browsers enumerate displays and choose window placement. Feature-detect it, ask only when arranging displays, and retain manual movement. It adds display placement control without adding transparent or always-on-top windows. [Window Management](https://developer.chrome.com/docs/capabilities/web-apis/window-management)

## Transparency and input are separate requirements

A transparent rectangular window can visually resemble a cutout while still intercepting clicks over its clear areas. Decide whether those clear areas should move the toolbox, pass through to the canvas underneath, or expose a resize handle. Keep explicit drag and resize regions away from tool buttons and sliders. Electron supports toggling mouse ignoring with forwarded mouse movement on macOS and Windows. Tauri exposes cursor-event ignoring for the whole window. Neither establishes portable automatic click-through for every transparent pixel. Check stylus and touch behavior separately from mouse behavior. [Electron interactions](https://www.electronjs.org/docs/latest/tutorial/custom-window-interactions) · [Tauri window API](https://v2.tauri.app/reference/javascript/api/namespacewindow/)

On macOS, test full-screen Spaces, Mission Control, focus changes, Dock ordering, mixed Retina displays and unplugged monitors. Electron's native shape method excludes macOS and its stacking API documents platform-specific levels. Tauri's older advice about requiring the `macos-private-api` flag for transparency changed in 2.12.1, released September 30, 2026. That release removed the flag requirement. Check the chosen runtime version and distribution requirements directly before making an App Store commitment. [Electron BaseWindow](https://www.electronjs.org/docs/latest/api/base-window) · [Tauri 2.12.1 release](https://v2.tauri.app/release/tauri/v2.12.1/) · [Tauri configuration](https://v2.tauri.app/reference/config/)

## Keeping the party coherent

Keep the main party as the owner of selection, palettes, turn state and the call. Tool windows send validated commands and receive current state. They should not join as extra guests, start another call, replay full painting histories, or render another room. Save each window's layout separately, restore focus on return, provide keyboard move/resize controls and a “Gather toolboxes” action, and recover gracefully when a window closes or a monitor disappears. These are proposed implementation requirements, extending the existing [workspace brief](PAINTING-WORKSPACE.md).

A desktop shell adds packaging, signing, updates and a privileged message boundary. Limit toolbox commands, validate senders, keep Electron renderers sandboxed with context isolation and no Node integration, and scope Tauri permissions to the required windows and actions. Extra windows also add webview, image and compositor costs. Measure several open toolboxes on the older-machine baseline before selecting a runtime. No performance benefit follows from using a desktop shell alone. [Electron security](https://www.electronjs.org/docs/latest/tutorial/security) · [Tauri capabilities](https://v2.tauri.app/security/capabilities/)

The browser path can deliver movable tool windows, with optional single-toolbox PiP. The complete desktop-cutout vision calls for a native window host. A small desktop feasibility check should compare Electron and Tauri with two transparent trays, resize handles, clear-area input handling, focus restoration, and monitor changes before choosing one. No desktop runtime or window implementation has been added by this research.
