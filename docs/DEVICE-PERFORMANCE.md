# Drawing on older computers, tablets, and phones

Research for the pre-test pass, November 6, 2026. The goal is a full party on one device, with a second device available as an optional way to split up the work.

## What the app already does

- [PartyCanvas](../apps/web/src/lib/canvas/PartyCanvas.svelte) applies local marks before sending them over the socket. It batches display compositing to one animation frame and batches mouse and pen stroke messages on a 50 ms timer. The touch path holds the initial batch briefly so an emerging two-finger gesture can cancel the tentative mark. The `?perf` or `&perf` readout already reports move time, stamp rate, and redraw cost.
- [TurnLayers](../apps/web/src/lib/canvas/layers.ts) keeps a full-resolution canvas per painter and round. A 1600×1200 RGBA surface is about 7.3 MiB before browser overhead. The visible canvas, touch backups, snapshots, and GPU copies can raise peak memory. A small CSS viewport still uses the same underlying painting dimensions. Inspect peaks during pinch, turn changes, and late join, alongside average frame time. The turn snapshot still uses synchronous PNG encoding even though a Blob path exists for other saves.
- [Studio](../apps/web/src/lib/Studio.svelte) already lazy-loads the 360° room and gallery. The painting table stays mounted when hidden so it can keep its layers. [The call client](../apps/web/src/lib/call/call.svelte.ts) enables adaptive stream and dynacast, but passes raw `MediaStreamTrack` objects to a helper that assigns `srcObject`. LiveKit JS documents `Track.attach()` as a prerequisite for adaptive stream. Verify SDK attachment and detach behavior before relying on hidden or small tiles to save decoding work. [LiveKit subscriptions](https://docs.livekit.io/transport/media/subscribe/) · [LiveKit room options](https://docs.livekit.io/reference/client-sdk-js/interfaces/RoomOptions.html)

## First pass before testing

1. **Give painting the frame budget.** Offer Auto and a persistent manual Paint priority override. Keep the same canvas, tools, timer, seat controls, chat, accessible controls and audio. In Paint priority, start with a static room view or the seat list, compact avatars, and an explicit control to restore guest video. Reduce or pause video subscriptions through LiveKit, including when video is hidden in the painting layout. Keep the user's own camera and microphone choices independent. Confirm actual decode and publish cost with a real call. [LiveKit subscriptions](https://docs.livekit.io/transport/media/subscribe/)
2. **Measure the work in front of the user.** Sample frame gaps, stamp work, and compositing during active painting only. Compare against the observed display cadence, which can differ by screen and power mode. Ignore backgrounded tabs, first-load spikes and intentional idle periods. After sustained pressure, lower optional effects or video load. Upgrade only after a stable period between strokes to avoid flicker. Keep measurements local and ephemeral. Feature-detect optional APIs and use `deviceMemory` only as a coarse, optional hint. It is rounded, clamped and unavailable in some browsers. Screen width informs layout. A device name or touch support alone says little about spare compute. [Animation frames](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame) · [Device memory](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/deviceMemory) · [Long animation frame diagnostics](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing)
3. **Optimize the expensive path before changing paint quality.** Profile the touch backup pool and whole-canvas compositing as the turn stack grows. Try bounding retained scratch buffers, replaying long histories in bounded chunks, and caching composites where painter ownership permits it. Check the snapshot allocation and encoding separately. Any asynchronous snapshot path needs a frozen image and the original round and canvas IDs so a turn change cannot save the wrong picture. Keep authoritative dimensions, pressure, seeded stamp indices, tool behavior, and editable ownership consistent across devices. A display-only preview can scale down first if profiling shows that presentation is the bottleneck. [Canvas rendering and serialization](https://html.spec.whatwg.org/multipage/canvas.html)
4. **Add optional input and rendering accelerators only with evidence.** Test `getCoalescedEvents()` where available to preserve curvature and pressure on fast pen strokes, with ordinary pointer events as fallback. Coalesced samples can increase stamp work, so measure dense strokes before enabling broadly. Keep touch gesture handling separate from pen pressure and preserve the keyboard path. Predicted points, if tested, belong in a temporary visual overlay and never in saved or relayed strokes. A worker with `OffscreenCanvas` may free the UI thread if rasterization dominates, but adds message and synchronization work and does not inherently reduce bitmap memory. Test it behind capability detection and keep the current 2D path. [Pointer Events](https://www.w3.org/TR/pointerevents3/) · [OffscreenCanvas](https://html.spec.whatwg.org/multipage/canvas.html#the-offscreencanvas-interface)

## Two devices

| Approach | What it buys | What to test |
| --- | --- | --- |
| Apple Sidecar | A supported Mac renders the browser while a supported iPad acts as its extended or mirrored display with Apple Pencil input. This is an immediate benchmark with no app changes. | Try USB and wireless. Check browser pressure, pen latency, and whether the painter can see the party while the canvas is on the iPad. Apple's Pencil support does not establish browser pressure behavior for this app. [Apple Sidecar](https://support.apple.com/en-us/102597) |
| Native companion canvas | The iPad, phone or second computer renders the local stroke immediately and runs the paint UI. The laptop handles camera, mic and optionally the room. Both share one party seat and turn. The companion skips 360° and call subscriptions so it has more capacity for drawing. | Test same-network and separate-network sessions, device swaps during a turn, reconnects, and a sleeping tablet. Use the existing stamp stream for painting after the server has bound the companion to the seat. |
| Remote-rendered canvas | A laptop handles raster work and streams a paint-only surface. The tablet sends pointer input back over a separate channel. | Measure the input trip to the laptop plus the render, encode, return, decode and display steps. A local ink preview could hide some delay but must reconcile with the returned frame, especially for blending and erasing. Screen capture provides a media stream and does not provide remote pen input. Capture also has permission and browser-support constraints. [Screen Capture specification](https://www.w3.org/TR/screen-capture/) · [Browser support](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia) |

For an app-supported split, start with a native companion. Today the [party server](../apps/server/src/party.ts) gives each joining socket its own member ID and attributes strokes and turns to that ID. A second ordinary join therefore represents another guest. Use an expiring, one-time pairing code or link minted by the current party connection, plus a manual code path alongside QR. Authorize companion access at the server. Use one seat ID and a single, revocable paint lease, separate from the primary call connection. On handoff, finish or cancel the in-progress stroke, initialize the new writer from ordered canvas history and current turn state, then grant input. Reject late writes from the old lease and require confirmation to transfer control back. Test disconnects of either endpoint, duplicate pair attempts, missed history, and stale snapshots. A companion should never advance turn order by joining, start another camera session, or gain host powers. This is a protocol design for the existing [roadmap item](ROADMAP.md). The single-device path remains the test baseline.

## Device checks

Use an older laptop, a phone as the only device, and an iPad with Pencil plus finger gestures. On each, compare avatar or audio-only, camera with visible guests, and room-to-canvas transitions. Run short marks, long fast curves, touch-to-pinch, blending and erasing across owned turns, a late join to a large canvas history, and a snapshot at pass. Exercise keyboard and screen reader controls at both narrow and wide layouts.

Record p50 and p95 frame gaps and stamp/composite time from the same scripted sequence. Use high-speed external capture for true pen-to-pixel latency if available. Distinguish that from remote stroke arrival, which includes network and batching. Start by looking for marks within one or two display refreshes locally and for long stalls during input or pass. Check that one-device painting, turn completion, snapshot recovery, and media controls all still work in the lower-cost configuration. Actual hardware results are still pending.
